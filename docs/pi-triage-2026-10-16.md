## 3. Ranked findings

### 1. `jittersim-mdns.service` has been dead for 6 days (dashboard name `netlab.local` is not announced). USER-VISIBLE

- Evidence (journal, the whole life of the unit):
  ```
  2026-10-10T13:22:35 systemd[1]: Started jittersim-mdns.service - Announce the dashboard name on Ethernet and the test Wi-Fi.
  2026-10-10T13:22:35 systemd[1]: jittersim-mdns.service: Sent signal SIGHUP to main process 984 ((python3)) on client request.
  2026-10-10T13:22:35 systemd[1]: jittersim-mdns.service: Deactivated successfully.
  ```
  `systemctl show`: `ActiveState=inactive SubState=dead Result=success ExecMainStatus=1 NRestarts=0`.
  `/run/jittersim-mdns` does not exist, so there is no status file. `netlab.local` (from `/etc/jittersim/trust.env`)
  does not resolve from the Mac (ping times out, dscacheutil empty). Avahi has `publish-addresses=no`, so nothing else
  announces it. The dashboard still opens by IP 192.168.0.17.
- Count: 1 occurrence, but the effect lasts from 2026-10-10 13:22 until someone starts it.
- Root cause: boot-time race. The same second the unit started (NetworkManager had just reached CONNECTED_GLOBAL and
  activated eth0 and wlan0), the NM dispatcher hook sent `SIGHUP` to the main process. The process was still named
  `(python3)`, which is systemd's pre-exec name, so Python had not yet installed its SIGHUP handler. Default SIGHUP
  action is terminate. systemd counts SIGHUP as a clean exit (`SuccessExitStatus` default), so `Restart=on-failure` never
  restarts it. Code path:
  - Hook: `deploy/raspberry-pi/jittersim-mdns-dispatcher` (installed as `/etc/NetworkManager/dispatcher.d/80-jittersim-mdns`)
    runs `systemctl kill --kill-whom=main --signal=HUP jittersim-mdns.service` on up, down, dhcp4-change, reapply of the uplink or test interface.
  - Handler installed late: `src/jittersim/mdnsname.py` `_publish_command()` (lines about 755 to 781) builds `Publisher(...)`,
    reads the name and runs `_extra_names()` (spawns openssl, up to 5 s) BEFORE `signal.signal(SIGHUP, on_wake)` at line 781.
  - Unit: `deploy/raspberry-pi/jittersim-mdns.service` has `Restart=on-failure`, so a SIGHUP death is not retried.
  - Introduced in 87bf2cb (2026-09-29 "Publish dashboard name over mDNS").
- Fixed on main: **NO.** `mdnsname.py`, the unit and the dispatcher are byte-identical on the Pi, at 4b343b6 and on main
  (sha256 of mdnsname.py and the unit match, `git log 4b343b6..origin/main` is empty for all three files).
- Proposed fix:
  1. Immediate, owner action with root: `sudo systemctl start jittersim-mdns.service` (safe, only announces the name).
  2. Code: in `mdnsname.py` install the SIGTERM, SIGINT and SIGHUP handlers as the very first statements of
     `_publish_command` (or `main`), before any slow work. Set `Restart=always` or `RestartForceExitStatus=SIGHUP` in the unit so
     a stray SIGHUP can never leave it dead. Optionally make the dispatcher use `systemctl kill` only when `is-active`
     returns active. Add a unit test that sends SIGHUP right after start.
- Risk: low. Name publisher only. Deploying main alone does not fix it, but `install.sh` ends with
  `systemctl restart jittersim-mdns.service`, so a deploy would revive it until the next reboot, where the race returns.

### 2. Journal is volatile (RAM only), so evidence is lost at every reboot. INDIRECTLY USER-VISIBLE (blocks diagnosing outages)

- Evidence: `/usr/lib/systemd/journald.conf.d/40-rpi-volatile-storage.conf` contains `Storage=volatile`.
  `journalctl --list-boots` shows one boot. `/var/log/journal` is empty (dir dated 2026-09-15). The Pi has no
  `/etc/jittersim-outage-journal`, no `/usr/local/lib/systemd/journald.conf.d` and no `journal_policy.py` in the installed tree.
- Root cause: Raspberry Pi OS default. The deployed release has no journal policy at all.
- Fixed on main: **NO, not effectively on this Pi.** Main adds `src/jittersim/journal_policy.py` (ef73389, e9c8780, via PR #91),
  and `install.sh` (lines about 410 to 417) runs it as an optional step. But `inspect_policy()` treats any journald drop-in
  that sets a known option, including the vendor file under `/usr/lib/systemd`, as an administrator choice and raises
  `administrator-policy`. I reproduced this locally (scratchpad `sim-roots`, a copy of the Pi's drop-in) and got
  `PolicyError: administrator-policy`. So after a deploy the installer prints "optional outage journal setup was skipped"
  and the Pi stays volatile. The repo README (`deploy/raspberry-pi/README.md` line about 1431) documents this as a known limit
  ("Raspberry Pi OS may ship a volatile storage default ... ask for a decision"). Even if it ran, the policy file sorts as
  `20-jittersim-outage.conf` and Pi OS's `40-rpi-volatile-storage.conf` would win because later names override earlier ones.
- Proposed fix: owner decision needed. Either (a) accept the Pi OS vendor drop-in as a distribution default (not an admin choice)
  and install the policy under a name that sorts after it (for example `50-jittersim-outage.conf`), or (b) manually, with root:
  create `/etc/systemd/journald.conf.d/40-rpi-volatile-storage.conf` with `[Journal] Storage=persistent SystemMaxUse=64M MaxRetentionSec=7day`
  then `systemctl restart systemd-journald`. Observed card writes are tiny (about 55 MB in 6 days), so the 64 MB cap is low risk.
- Risk: low to medium. Touches journald and SD wear (bounded to 64 MB). Power loss can still lose the newest lines.
