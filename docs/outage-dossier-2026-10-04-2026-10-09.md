# Outage dossier: router failures during Pi-only Wi-Fi (4 to 9 October 2026)

Read-only evidence review written on 9 October 2026. Nothing on the Pi or the
router was contacted or changed. All times are Berlin time (CEST) unless marked.

## Summary

There were **three separate events**, not one. Earlier notes mixed them up.

| Event | When | What happened | Red PHONE | Router restart needed |
| --- | --- | --- | --- | --- |
| A (two failures) | night 3/4 Oct, about 00:13 to 01:12 | Pi copied the router name, router Wi-Fi off, `daily climb manual` profile applied. No internet, router Wi-Fi then refused the right password even with the Pi unplugged | yes, twice | yes, twice (second at about 01:12) |
| B | 4 Oct, some time between 17:21 and 20:14 | Pi already had the router name, owner switched router Wi-Fi off. Two devices joined but could not browse. Router Wi-Fi back on did not help | yes, a few minutes after Wi-Fi was back on | yes (at about 20:18) |
| C (trial) | 4 Oct, 22:05 to 22:43 | Controlled 10-minute trial with profiles off. Both Macs browsed through the Pi with router Wi-Fi off. Later the router logged `AP-DISABLED` three times and its Wi-Fi was found off | no report | no (uptime continuous) |

Most probable explanation (about 60 percent, judgement): **the Vodafone Station
itself hangs** (internet routing, telephone registration and Wi-Fi log-in all
stop together and only a power cycle helps), and the hang was **triggered by
something during Pi-only operation**. The leading trigger is the shaped traffic
of the `daily climb manual` profile (packet corruption, duplication, reordering
and loss on everything the Pi forwards). It was certainly active in event A and
was very likely started in event B. The two Pi-only runs without that profile
(68 minutes on 4 October afternoon, about 15 minutes in event C) did not break
the router. This is a correlation from three events, not proof.

What the evidence rules out or nearly rules out:

- JitterSim sending the `KickAssocDevices` command at 01:14:58. The router logs
  web-page changes as `from WEBGUI`. `CLIENTTOOL` is the write identity of the
  router's internal command-line tool (`dmcli`). An unrelated Vodafone Station
  owner logged the same `CLIENTTOOL` line with no Pi in the house.
- JitterSim switching the router radios off at 22:24 to 22:29. JitterSim made no
  router contact in event C at all (the agent changed only the Pi's name over
  SSH) and the router log has no `WEBGUI` change in that window.
- MAC filtering. It was switched on at about 22:47 to 22:54 and off at 22:55,
  after all three events.
- Automatic router polling as a necessary cause. The 15-second polling was
  removed before event B (in release 081b2ab, installed about 15:15 on 4 October)
  and event B still happened.
- A Pi data path that is broken in general. The Pi carried working internet in
  the afternoon cutover and in event C.

Three observations would settle it (details in the checklist below):

1. Read the Pi's saved action history for 4 October 17:00 to 20:30 (read-only).
   It shows whether a profile was started, the router switch was used or the
   copy ran before event B.
2. One button test with the Pi powered off: press the router Wi-Fi button off,
   wait three minutes, press on, export the event log. This shows what one
   press writes and explains the event C log lines.
3. A long Pi-only run with **all impairments off** (two to three hours) with the
   passive capture running, then the same with **delay and jitter only**. If the
   router stays healthy, the corruption/duplication profile becomes the main
   suspect. If it fails anyway, a capture taken before the power cycle shows
   which router function died first.

## Hypotheses, ranked

### 1. The router hangs, triggered by Pi-only operation (about 60 %)

The symptoms span three separate router functions at once: forwarding to the
internet, telephone registration (PHONE red means "at least one phone line could
not register" in Vodafone's guide) and Wi-Fi log-in (the 30-second wait then
"could not connect" is a handshake timeout, not a wrong password). They survive
unplugging the Pi and clear only after a power cycle. The DOCSIS cable link was
probably still up (INTERNET light likely white). That pattern fits a stuck
router (software or packet engine), not a cable fault and not the Pi.

A late red PHONE fits too: telephone registration is refreshed periodically, so
the light turns red some minutes after the router stops passing traffic. This
part is reasoning, not measured.

Candidate triggers, best first:

- **Impaired traffic** from `daily climb manual`. `netem` flips random bits
  (corruption), sends copies (duplication) and swaps order. The Pi forwards all
  of that to the router, which carries IPv4 over a DS-Lite tunnel. How the
  TG3442DE (Intel Puma 7 chipset per forum reports) handles damaged headers in
  volume is unknown. Profiles-off runs were fine; profile-on runs failed.
- **Router Wi-Fi off and on** while most household devices move to the Pi.
  Happened in all failures but also in both successful runs, so not enough on
  its own.
- **Repeated router log-ins** (event A only). Not present in B.

What would settle it: a long Pi-only run with impairments off and the capture
running (no failure expected), then delay and jitter only (the owner's reduced
scope). Before any power cycle, a failure capture showing whether the Pi can
still reach 192.168.0.1 and whether the router page still answers.

### 2. The router hangs by chance (about 15 %)

Forum owners report Vodafone Stations that need a power cycle, `AP-DISABLED`
lines and `CLIENTTOOL ... KickAssocDevices` lines with no Pi at all. Against it:
three red-PHONE failures fell inside the only windows with cutover activity.
Settle: ask the owner whether PHONE ever turned red before JitterSim, and log
the router for a week of normal use (count `AP-DISABLED`, restarts, red PHONE).

### 3. Clients stuck in a split state (contributor only, about 10 %)

A device that held a 192.168.0.x lease can join the Pi under the same name and
keep that address until DHCP renews. That can explain "connected but cannot
browse" at the start of event B. It cannot explain the router refusing Wi-Fi
log-ins after the Pi was unplugged or the red PHONE. Settle: during the next
run, the Pi's dnsmasq log shows `DHCPNAK ... wrong network` or new leases, and
the client's `ipconfig getifaddr en0` shows the subnet.

### 4. JitterSim wrote to the router or logged in and disturbed it (about 10 %)

Largely ruled out for the logged events (see Summary). Remaining open: whether
the whole-form Wi-Fi write at 00:13:54 (it re-sends all general Wi-Fi fields
through the router's own web endpoint) or an hour of log-ins every 15 seconds
destabilised the router in event A. Router Wi-Fi writes are now refused (PR 87)
and polling is manual, so this path is already closed for future runs.

### 5. Pi data path broken (not supported as the main cause)

The Pi forwarded fine at 15:48 and 22:20 with profiles off. Cannot explain the
router-side symptoms. The capture checklist still records it.

### 6. Pi pollutes the household LAN (low, under 5 %)

No evidence of a DHCP server, router advertisements, LLDP or a loop on `eth0`.
The AP subnet is separate and NetworkManager's dnsmasq is bound to `wlan0`. Any
such fault would stop when the Pi was unplugged, but the router stayed broken.
Settle: a two-minute `tcpdump` on `eth0` for packets sent by the Pi (command
below) should print nothing.

### 7. The `AP-DISABLED` lines in event C come from button presses or radio restarts

Likely for at least some lines. Each radio restart reruns channel choice, which
matches the 2.4 GHz channel moving 5 → 1 → 5. Another owner's Station log shows
`AP-DISABLED` in pairs after one Wi-Fi change. The owner denies pressing the
button at 22:29. The router may also restart radios itself. This explains the
log lines, not the red-PHONE failures. Settle with the button test.

### Design finding (not a cause)

The rollback timer in event C restored the Pi's name at 22:15:44 while router
Wi-Fi was still off. For about five minutes no access point used the router
name. The Macs only kept working because they auto-joined the known
`JitterSim-Recovery` network. A household device would have lost Wi-Fi. A safe
rollback must also tell the owner to switch router Wi-Fi back on first, or the
timer must wait for that.

## Specific questions

- **Why did router clients fail with the Pi unplugged?** Because the router
  itself was stuck. The Pi cannot block the router's own Wi-Fi handshake.
- **Can anything on the LAN turn PHONE red?** Not directly. The phone line is
  provisioned over the cable side. A LAN device can only cause it indirectly
  by making the router itself stop working.
- **Pi behaviour as the router sees it:** one wired client on LAN port 1 at
  1 Gbit/s, a DHCP client, NAT for 192.168.50.0/24. `netlab.local` was not
  being announced. No known Vodafone Station fault is tied to such a client.
- **Does the router button write `AP-DISABLED`?** Very likely, but unmeasured.
- **The 01:14:58 `KickAssocDevices`:** written about three minutes after the
  01:12 power-on by the router's own command-line tool identity. It matches the
  same line on an unrelated Station. Not JitterSim.

### 3. Pi-only run with captures

Start a capture folder on the Pi:

```sh
mkdir -p ~/capture && cd ~/capture
date -Is > start.txt; cat /proc/sys/kernel/random/boot_id >> start.txt; uptime >> start.txt
sudo jittersim status > status-before.txt
sudo tc -s qdisc show > qdisc-before.txt
sudo tc qdisc show | grep -E 'corrupt|duplicate|reorder|loss' && echo 'IMPAIRMENT ACTIVE, STOP'
ip -br link > net-before.txt; ip -br addr >> net-before.txt; ip route >> net-before.txt
sysctl net.ipv4.ip_forward >> net-before.txt
nmcli -g 802-11-wireless.ssid,802-11-wireless.band,802-11-wireless.channel connection show jittersim-ap > ap-before.txt
iw dev wlan0 info >> ap-before.txt
journalctl --list-boots | tail -3 > boots.txt
```

Check the Pi is not sending server traffic onto the household LAN (two minutes,
should print nothing):

```sh
PI_MAC=$(cat /sys/class/net/eth0/address)
sudo timeout 120 tcpdump -i eth0 -n -e "ether src $PI_MAC and (udp src port 67 or (icmp6 and ip6[40] == 134) or ether proto 0x88cc)" | tee lan-check.txt
```

Start the background recorders (they stop on reboot or with `sudo pkill -f capture-loop; sudo pkill tcpdump; pkill ping`):

```sh
nohup ping -D -i 1 192.168.0.1 > ping-router.txt 2>&1 &
nohup ping -D -i 1 1.1.1.1 > ping-internet.txt 2>&1 &
nohup sh -c 'while :; do date -Is; curl -sS -m 5 -o /dev/null -w "%{http_code} %{time_total}\n" https://example.com; sleep 10; done' > http.txt 2>&1 &
sudo nohup sh -c 'while :; do date -Is; iw dev wlan0 station dump | grep -c ^Station; wc -l < /var/lib/NetworkManager/dnsmasq-wlan0.leases; cat /proc/sys/net/netfilter/nf_conntrack_count; ip neigh show dev eth0 192.168.0.1; sleep 30; done # capture-loop' > pi-state.txt 2>&1 &
sudo nohup tcpdump -Z "$USER" -i eth0 -n -s 96 -G 600 -W 18 -w 'eth0-%H%M.pcap' 'not port 22' > /dev/null 2>&1 &
sudo nohup journalctl -f -o short-iso-precise > journal.txt 2>&1 &
```

The packet capture keeps only headers, rotates every 10 minutes and keeps three
hours. `tcpdump` and `ping` are mature standard tools; no custom code is needed.

On the router page, before switching router Wi-Fi off, note: uptime, date and
time, both bands with channel, PHONE and INTERNET light colours (a photo with a
visible clock is best). Then switch router Wi-Fi off with the button and write
down the exact time. Note the time of every later button press and every router
setting change.

Run order: first **two to three hours with all impairments off**. Only if that
stays healthy, a second run with **delay and jitter only** on KPMac and
KPiPhone. Never corruption, duplication, reordering or loss on the household.
