# Dashboard concurrency audit and repair plan

The threaded dashboard improves responsiveness but its current worker ownership and Panic recovery need repair before release. Keep the bounded worker model and shared database lock. Repair worker startup and shutdown first, preserve Panic across queued applies and failed cleanup, then tighten shared scan invalidation and page transfer rules. These changes affect network recovery so passing ordinary tests alone is insufficient.

This is a read-only source audit of combined branch `feat/deploy-without-ssh` at `1edf97a6038a5b3c09d7c95ce4536e06ba6507aa`. PR #70 is already included through merge `5e95b8c`. The original `perf/server-concurrency` branch must remain unchanged. The combined branch owner implements repairs. This audit does not authorize publication or live Pi changes. Final combined verification and publication belong to the release coordinator.

## Release blockers

1. **Worker startup can release ownership twice.** `src/jittersim/api/server.py:11140` increments capacity before starting a thread. Its exception path decrements capacity and closes the request. The worker also decrements capacity at `11168`. If startup begins the worker then raises, capacity can go negative and an active socket can be closed by the parent. `src/jittersim/networking/helper.py:1288` has the same parent/worker release problem with its bounded semaphore. Preserve exactly one owner of each permit and request across failure before startup, failure after startup and normal completion. Reproduce with a thread start hook that starts the real worker then raises. Include immediate worker completion and repeated failures. Verify no early slot reuse, no negative count, no extra semaphore release and no double socket cleanup.

2. **Shutdown does not retain active dashboard ownership.** The server uses daemon workers with `block_on_close = False` at `src/jittersim/api/server.py:11082`. `server_close()` at `12848` closes pending connections and router state but does not drain active request workers. `run_server()` at `15298` then exits the repository context. An active helper call can return later against a closed database. A successful late apply can also activate the scheduler after its stop. Stop admission first, retain worker and request ownership until completion and dispose of shared state only when no request can use it. Define a finite shutdown limit and an explicit failure outcome for a worker that cannot finish. A join timeout does not establish completion. Test shutdown during input, helper apply and response send. Verify no database access or scheduler restart after shutdown completes. Preserve the helper's existing non-daemon worker drain behavior.

3. **Failed Panic cleanup is recorded as success.** `src/jittersim/api/server.py:14053` catches a failed late-apply undo but still records `reset` with `success` at `14065` and reports that Panic stopped the apply. Report failure or unconfirmed restoration when cleanup fails. Keep automation paused. Test failed undo, failed state persistence and a successful retry. Assert both the response and saved state. The earlier helper apply failure branch at `13992` also records an apply failure without checking whether Panic overtook it. Preserve Panic's ownership of recovery while reporting any unresolved helper failure truthfully.

4. **An Apply queued before Panic can restart afterward.** `_apply_configuration()` at `src/jittersim/api/server.py:13935` waits for the scheduler lock before `_apply_configuration_locked()` captures `halt_count` at `13950`. A second explicit Apply already waiting before Panic therefore treats the new halt generation as its starting point. Capture request intent before waiting and refuse obsolete applies after Panic. A fresh Start sent after Panic must still work. Reproduce with blocked Apply A, queued Apply B, Panic and then release A. Assert B cannot restore impairment or resume scheduling. Check auto-apply write routes for the same gap.

5. **Invalidated scans still return old identity data.** `src/jittersim/networking/helper.py:1745` starts a new scan after an invalidation but old leaders and waiters still return the old value at `1752` and `1765`. The generation check only prevents cache storage. Current tests at `tests/unit/test_helper_snapshot_cache.py:124` and `158` check later cache reuse but discard the original caller's result. Reject or retry invalidated results within a bounded deadline. Tests must capture both leader and waiter results when a network change occurs during a scan. Prevent the invalidated identity from reaching profile eligibility or saved address moves. Preserve the intentional short stale fallback only while its identity generation remains valid.

## Other required checks and bounded follow-ups

- **Panic admission under saturation.** There are 16 ordinary dashboard workers and two reserve workers. Classification occurs after complete headers at `src/jittersim/api/server.py:14223`. Two ordinary slow header requests can occupy the reserve until their input deadlines. The helper separately caps all connections at eight without a Panic reserve at `src/jittersim/networking/helper.py:1288`. Existing tests check a single busy ordinary worker followed by complete requests. Add a deterministic saturation case with incomplete requests occupying both reserve slots and a real helper connection limit. Require a bounded, documented recovery path. Do not describe reserve capacity as an unconditional guarantee that Panic always gets in.
- **Scan deadlines and overlap.** `flight.done.wait()` at `src/jittersim/networking/helper.py:1749` has no caller deadline. Each new invalidation can replace the tracked scan while an older scan remains active. Define a total caller deadline and a finite bound on in-flight scans. A socket inactivity timeout at `1989` is not a total deadline. Test repeated invalidation, failed scan, waiter cancellation and a response that trickles bytes. Do not silently convert a timeout into a verified client identity.
- **Consistent database ownership.** `ConfigRepository` at `src/jittersim/config/storage.py:167` shares one SQLite connection behind a re-entrant lock. `transaction()` at `194` holds that lock across the whole block. The method wrappers at `3673` and `src/jittersim/config/workflows.py:254` protect the shared connection. No unguarded connection use outside these owning modules was found. Keep lock order consistent with scheduler ownership. `_save_service_list()` at `src/jittersim/api/server.py:13223` calls `_validate_saved_plan()` inside the repository transaction. This reaches website resolution in `src/jittersim/engine/service.py:23`, whose shared lookup allowance is ten seconds in `src/jittersim/engine/website.py:30`. Panic needs repository reads before contacting the helper, so a reserved worker alone does not remove this wait. Test this boundary and avoid holding the repository lock across slow external work. Audit multi-method writes for an atomic state transition rather than relying on each individual method lock.
- **Page transfer correctness.** `_accepts_gzip()` at `src/jittersim/api/server.py:10464` uses the first wildcard or gzip item. It will incorrectly compress for `*;q=1, gzip;q=0`. The same strong ETag identifies compressed and uncompressed bytes at `10452` and `14476`. Select the representation first, honor explicit gzip refusal regardless of item order and use a valid weak validator or separate strong validators. Conditional GET should handle weak comparison. Keep JSON responses uncompressed with `no-store` and preserve security headers on 200 and 304. Add focused transfer tests. [RFC 9110 encoding rules](https://www.rfc-editor.org/rfc/rfc9110.html#section-12.5.3) and [representation validators](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.3.3) support these corrections.
- **Scheduler race boundaries.** Inspect `src/jittersim/engine/runtime.py:673` through result recording. Test Panic immediately after the post-helper halt check as well as inside the helper call. Preserve stopped state when helper undo or runtime persistence fails. The existing scheduled race test only places Panic inside the helper apply.
- **Honest scope.** Startup recovery remains synchronous in `run_server()`. `/api/plan` still takes the scheduler apply lock. HTTP/1.1 keep-alive is not enabled. These are deliberate follow-ups unless the combined release owner explicitly adds them. Do not imply this PR completes all dashboard responsiveness work.

## Persistent Panic guard extension

The coordinator extended this scope to preserve Panic across complete service stops and reboot. Current gateway state lives under `/run/jittersim`, which does not survive reboot. Access boot also restores household rules before the helper reads that state. If Panic cannot write SQLite then an old saved Apply can therefore resume. RuntimeDirectory preservation across an individual stop depends on the other units sharing that directory. No unconditional deletion claim is made for a helper-only stop.

Store a separate root-only record at `/var/lib/jittersim-control/panic-state.json`, outside ordinary data and release backups. Keep its format bounded and strict. Open the file and its directory without following links. Require root ownership and private modes. Write through an exclusive temporary file then sync the file and directory. Record stopped shaping, unconfirmed recovery and the permanent requirement for a fresh helper control revision. Each helper process creates a new control revision.

Both access boot and helper startup must read this record before restoring household rules. Stopped or damaged state permits only the disabled-access recovery path. Existing state with a missing or unreadable record requires recovery. A first installation with no guard directory may migrate the current gateway flags then initialize its record before restoring access. A failed initialization must not restore an enabled policy. Startup does not convert an unconfirmed Panic into a successful one.

Panic persists its unconfirmed stop before cleanup and confirms recovery only after cleanup and both state writes succeed. Fresh explicit Start clears the stopped flag only after successful apply and durable state publication. A failed guard write keeps Start blocked and requires a fresh Panic. No outage marker changes are proposed.

The update owner will retain this record outside package and settings replacement. Its standalone manager must read the current record after writers actually stop, reject a rollback package that cannot preserve stopped shaping and disabled household access before destructive replacement, then preserve the current record through service startup. The hook must work without importing the replaced virtual environment. Candidate support needs an explicit verified format marker and actual old-reader tests rather than a version comparison. Freeze the helper guard and the standalone hook together before final independent review.

The independent reviewer approved this extension before implementation on 3 October. This approval covers the direction. Final approval must cover the exact source and tests. Verification must include a Panic with failed SQLite writes, deletion of runtime files, actual helper and dashboard reconstruction, both access startup callers, malformed records, symlink rejection, failed syncing, fresh Start and obsolete helper intent. Final Linux service ordering and installer rollback checks remain with the coordinator.

Once Panic has required the helper intent fence, that requirement remains after a fresh Start. Refuse an older rollback package that cannot honor it even when profiles currently run. The updater must explain that the selected package cannot preserve Panic protection. The guard must remain outside rollback snapshots and must never be cleared by an updater. Candidate compatibility is a source contract with reviewed evidence, not an unused advertised capability.

## Independent household intent

Panic stops profile shaping and household restrictions. They remain separate controls afterward. A fresh household action must survive restart without starting profiles or clearing profile-stop intent. The coordinator approved a separate durable household-stop flag on 3 October. The independent reviewer agreed this direction before source changes.

Use a new strict record format with profile stop, household stop, failed recovery and the permanent control revision requirement. Panic sets both stop flags before cleanup. A fresh successful household operation changes only household intent after confirmed policy application and durable publication. A fresh Start changes profile intent after confirmed apply. Failure to save either transition must undo the affected mutation, keep unconfirmed recovery blocked and report failure. Startup uses household intent for access restoration and profile intent for automatic shaping.

Known complete version 1 records migrate household stop from profile stop conservatively. Missing or malformed old fields remain unsupported. Candidate compatibility requires the new reviewed guard, helper and access source bundle. The standalone producer must preserve known flags and must not invent state. Fresh installation requires explicit proof of absent installation witnesses under the real installer lock. Runtime-file absence alone is not that proof.

Verify actual helper and access boot consumers after fresh household re-enable while profiles remain stopped. Include reconstruction, failed state writes, stale household completion after Panic and fresh profile Start that does not silently enable household rules. Also check a Start queued before an external helper Panic so it cannot capture a new helper revision after its original wait.

An established persistent record also requires compatible startup consumers when all current flags are false. An unsupported old helper ignores that marker. A later Panic with failed settings writes followed by runtime loss can leave the old clear marker authoritative and restart obsolete profiles. The coordinator approved removing the clear-state exception. Refuse unsupported transitions before changing installed source. Keep first upgrades with unproven state and old rollback packages explicitly unsupported. Do not add an implicit recovery or clear-state fallback.

The installer may use a pure `inspect_upgrade(legacy_path)` eligibility check before creating its outer operation record or stopping services. This uses the same strict parser as provisioning and creates no guard state. Its result is a preview. After proving ownership and physically stopping writers the actual producer must read current state again. Never carry the parent's captured flags into that write. The coordinator approved this small follow-up after the isolated repair review.
